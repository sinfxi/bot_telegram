# نقشه مهاجرت رایگان FXI به Cloudflare

> وضعیت این سند: ممیزی اولیه کد و طرح اجرایی؛ هیچ ترافیک تولیدی به Cloudflare منتقل نشده است.
> شاخه مبنا: `feature/telegram-delete-assistant`
> شاخه مهاجرت: `cloudflare-free-migration`

## 1) تصمیم معماری

هدف، اجرای نسخه‌ای مستقل و قابل بازگشت روی Cloudflare Free است؛ بدون Workers Paid، Containers، سرویس پولی یا خاموش‌کردن Render.

- **Cloudflare Pages / Workers Static Assets:** میزبانی رابط‌های موجود پنل و فایل‌های استاتیک. تا حد امکان HTML/CSS/JS فعلی حفظ می‌شود.
- **Cloudflare Worker (TypeScript):** API پنل، احراز هویت و endpoint وب‌هوک تلگرام. فرایند دائمی یا Polling در Worker اجرا نمی‌شود.
- **Telegram Webhook:** دریافت updateها از تلگرام با HTTPS و secret token؛ پردازش هر update باید کوتاه، idempotent و دارای پاسخ سریع باشد.
- **D1:** منبع اصلی داده‌های پایدار پس از مهاجرت؛ مدل داده و SQL باید از PostgreSQL به SQLite/D1 منتقل شوند.
- **KV:** فقط کش و داده‌های کوتاه‌عمر غیرحیاتی؛ منبع حقیقت برای نقش‌ها، مجوزها، نشست‌ها، صف عملیات یا تاریخچه نخواهد بود.
- **Cron Trigger + جدول کارها در D1:** برای کارهای زمان‌دار و ارسال همگانی دسته‌ای. هر اجرا مقدار کوچکی کار انجام می‌دهد، checkpoint می‌زند و در اجرای بعد ادامه می‌دهد.

هیچ Worker، دامنه، webhook تلگرام یا deployment در این مرحله فعال نشده است.

## 2) یافته‌های ممیزی کد فعلی

فایل‌های بررسی‌شده:
- `zeus_bot.py` (حدود ۳٬۸۴۴ خط)
- `panel_auth.py` (حدود ۵۴۵ خط)
- `group_owner.py` (حدود ۶۴۱ خط)
- `panel_security.py`
- `monitor.py`
- `app.py`، `requirements.txt` و `README.md`
- فهرست تست‌های موجود

یافته‌های مهم:
1. برنامه با Python، Aiogram، FastAPI و Uvicorn ساخته شده است؛ اجرای مستقیم این برنامه در Workers امکان‌پذیر نیست.
2. ربات در دو نقطه `dp.start_polling(...)` را راه‌اندازی می‌کند. معماری Worker باید به webhook تغییر کند و هر دو مسیر polling حذف شوند.
3. لایه دیتابیس مستقیماً از `psycopg` و PostgreSQL استفاده می‌کند.
4. سه جدول اصلی در کد ساخته می‌شوند: `fxi_bot_state`، `fxi_chat_messages` و `fxi_community_messages`. طرح فعلی از `JSONB`، `BIGSERIAL` و `TIMESTAMPTZ` استفاده می‌کند.
5. پنل مالک، پنل مدیر و پنل مالک گروه endpointهای مجزا دارند. مسیرهای API و کنترل مجوزها باید در Worker به‌صورت صریح بازپیاده‌سازی شوند؛ صرفاً پنهان‌کردن دکمه در رابط کافی نیست.
6. خروجی پشتیبان موجود فقط سه جدول مشخص را صادر می‌کند و فایل آن حاوی اطلاعات حساس است؛ پیش از مهاجرت باید نسخه پشتیبان کامل و مستقل از دیتابیس تهیه و صحت آن بررسی شود.
7. مانیتور فعلی نیز به PostgreSQL و محیط اجرای Render متکی است و بخشی از طراحی Cloudflare محسوب نمی‌شود.
8. تست موجود شناسایی‌شده در پوشه tests عمدتاً مربوط به امنیت پنل است؛ برای منطق webhook، دیتابیس D1، idempotency، صف ارسال و مجوزها باید تست‌های جدید نوشته شوند.

## 3) نگاشت داده پیشنهادی

| PostgreSQL فعلی | مدل مقصد D1 | ملاحظات |
|---|---|---|
| `fxi_bot_state.data JSONB` | ستون `data_json TEXT` | JSON معتبر، نسخه‌بندی‌شده و اعتبارسنجی‌شده |
| `fxi_chat_messages` | `chat_messages` | شناسه عددی، کاربر، provider، متن و timestamp به ISO/INTEGER |
| `fxi_community_messages` | `community_messages` | ایندکس ترکیبی chat/message و chat/sender/message |
| state مدیریتی/داده تنظیمات | جداول نرمال‌شده در صورت نیاز | مدیران، نقش‌ها، مجوزها و تنظیمات حساس نباید فقط در یک JSON حجیم مدفون باشند |
| داده‌های موقت/OTP | `auth_challenges` و `sessions` | زمان انقضا و مصرف یک‌باره؛ ذخیره هش کد، نه کد خام |
| updateهای تلگرام | `telegram_updates` | کلید یکتا روی update_id برای جلوگیری از اجرای دوباره |
| عملیات طولانی | `job_queue` | وضعیت، تعداد تلاش، next_run_at و checkpoint |
| پیام‌های همگانی | `broadcast_jobs` و `broadcast_recipients` | ارسال دسته‌ای با محدودیت نرخ و قابلیت توقف/ادامه |

این نگاشت اولیه است. قبل از نوشتن migration SQL باید تمام queryها، ستون‌های واقعی و روابط داده با dump معتبر دیتابیس تطبیق داده شوند.

## 4) طراحی webhook و جلوگیری از اجرای تکراری

- endpoint اختصاصی مانند `POST /telegram/webhook` با بررسی `X-Telegram-Bot-Api-Secret-Token`.
- اعتبارسنجی ساختار update و ثبت `update_id` در D1 با قید UNIQUE.
- ثبت update و ایجاد کارهای لازم در یک batch تراکنشی D1.
- اگر update قبلاً ثبت شده باشد، بدون اجرای دوباره عملیات جانبی پاسخ موفق داده شود.
- پیام‌های حساس مدیریتی فقط پس از بررسی نقش، مجوز، شناسه chat و وضعیت عضویت اجرا شوند.
- پاسخ webhook سریع باشد؛ پردازش‌های طولانی از مسیر job table ادامه پیدا کنند.
- توکن تلگرام و کلید OpenRouter فقط در Worker Secrets نگهداری شوند و هرگز در فایل‌های مخزن یا پاسخ API ظاهر نشوند.

## 5) محدودیت‌های رایگان و کنترل هزینه

مقادیر مستندشده Workers Free:
- سقف ۱۰۰٬۰۰۰ درخواست Worker در روز.
- CPU هر درخواست HTTP: ۱۰ میلی‌ثانیه.
- D1: روزانه ۵ میلیون ردیف خوانده‌شده و ۱۰۰ هزار ردیف نوشته‌شده.
- فضای کل D1 در Free: ۵ گیگابایت.
- عبور از سهمیه روزانه D1 باعث خطای query تا reset روزانه می‌شود.

بنابراین:
- queryها باید ایندکس‌دار و محدود باشند؛ از full table scan و بارگذاری کامل تاریخچه اجتناب شود.
- برای عملیات گروهی pagination و batch کوچک الزامی است.
- نرخ ارسال تلگرام باید جداگانه رعایت شود.
- در صورت رسیدن به سقف، سامانه باید خطای کنترل‌شده نشان دهد و کارهای باقی‌مانده را از بین نبرد.
- قبل از فعال‌سازی عمومی، برای هر قابلیت برآورد مصرف و سقف هشدار تعیین شود.
- هیچ قابلیت Cloudflare پولی یا ارتقای پلن در این پروژه بدون تأیید صریح فعال نمی‌شود.

## 6) مراحل اجرایی و معیار عبور

### مرحله A — تکمیل ممیزی (در حال انجام)
- فهرست کامل endpointها، handlerهای Aiogram، SQLها، stateها و مجوزها استخراج شود.
- طرح دقیق D1 و ماتریس دسترسی تدوین شود.
- وابستگی‌های خارج از Cloudflare (Telegram و OpenRouter) مشخص شوند.

**معیار پایان:** هیچ endpoint یا عملیات مدیریتی ناشناخته و بدون مالک مشخص باقی نماند.

### مرحله B — اسکلت Cloudflare بدون ترافیک واقعی
- Worker TypeScript، تنظیمات Wrangler، D1 migrations و تست محلی ساخته شوند.
- health/readiness، router، لایه D1 و webhook verifier پیاده‌سازی شوند.
- از mock Telegram در تست‌ها استفاده شود؛ webhook واقعی ثبت نشود.

**معیار پایان:** تست خودکار مسیرهای پایه، امضای نشست و دسترسی‌ها موفق باشد.

### مرحله C — پنل و API
- رابط استاتیک فعلی تا حد امکان حفظ شود.
- APIهای پنل مالک و مدیر به قراردادهای جدید متصل شوند.
- کنترل مجوز در سمت سرور برای تک‌تک مسیرها آزمایش شود.

**معیار پایان:** نقش مالک، مدیر با مجوز محدود، مدیر بدون مجوز و نشست منقضی‌شده نتایج درست بدهند.

### مرحله D — منطق ربات و کارهای پس‌زمینه
- handlerها به webhook تبدیل شوند.
- moderation، welcome، group/channel settings و broadcast به‌صورت مرحله‌ای منتقل شوند.
- idempotency و صف کارها در برابر retry آزمایش شوند.

**معیار پایان:** تست سناریوهای واقعی با ربات آزمایشی و گروه آزمایشی موفق باشد.

### مرحله E — انتقال داده و آزمون تطبیقی
- ابتدا backup کامل PostgreSQL تهیه شود.
- داده در محیط آزمایشی D1 وارد شود.
- شمارش رکوردها، نمونه‌گیری محتوایی، timestampها، تنظیمات و مجوزها با منبع مقایسه شوند.

**معیار پایان:** شمارش و checksum داده‌های منتقل‌شده تطبیق داشته باشد و restore آزمایشی موفق شود.

### مرحله F — Cutover کنترل‌شده
- فقط پس از تأیید تست‌ها، webhook ربات به Worker آزمایشی/نهایی منتقل شود.
- پایش خطاها و صحت عملیات انجام شود.
- Render و PostgreSQL فعلی تا پایان دوره تثبیت و تأیید نهایی حفظ شوند.

**معیار پایان:** ربات، پنل‌ها، دیتابیس، ورود و عملیات اصلی در تولید تأیید شوند؛ سپس درباره حذف Render تصمیم جداگانه گرفته شود.

## 7) موارد مسدودکننده فعلی

- دسترسی خواندن به دیتابیس Render از ابزار فعلی برقرار نشد: اتصال خارجی به allowlist و TLS نیاز دارد و IP ابزار اتصال در allowlist نیست. بنابراین هنوز تعداد رکوردها، حجم واقعی داده و schema زنده تأیید نشده است.
- ZIP پروژه جایگزین backup دیتابیس نیست.
- توکن‌ها و secrets لازم برای محیط آزمایشی هنوز نباید در Git ثبت شوند.
- تا زمان backup و بررسی داده، هیچ migration یا حذف داده‌ای انجام نمی‌شود.

## 8) سیاست ایمنی و بازگشت

- شاخه اصلی و شاخه عملیاتی Render تغییر نمی‌کنند.
- همه تغییرات Cloudflare در همین شاخه مهاجرت و در صورت نیاز Pull Request جداگانه انجام می‌شوند.
- webhook تولیدی تا عبور از تست‌ها دست‌نخورده می‌ماند.
- migrationها باید نسخه‌دار، تکرارپذیر و دارای مسیر rollback باشند.
- هیچ منبع پولی، سرویس Containers یا پلن Workers Paid فعال نمی‌شود.
- هیچ داده‌ای از Render حذف نمی‌شود تا صحت نسخه مقصد و امکان بازگشت عملاً ثابت شود.

## 9) گزارش پیشرفت تا 2026-11-08

این بخش وضعیت واقعی کد شاخه مهاجرت را از موارد صرفاً طراحی‌شده جدا می‌کند.

### انجام‌شده
- Worker TypeScript با مسیرهای health/readiness و verifier وب‌هوک ساخته شده است.
- migrationهای D1 شماره 0001 تا 0003 تعریف شده‌اند؛ migration سوم ستون‌های قفل ورود مدیر را اضافه می‌کند.
- ورود مالک با OTP تلگرام، نشست تصادفی هش‌شده، کوکی امن و ابطال نشست پیاده‌سازی شده است.
- ورود دومرحله‌ای مدیر با نام کاربری و PIN چهاررقمی تعریف‌شده توسط مالک، سپس OTP شش‌رقمی تلگرام پیاده‌سازی شده است. PIN با PBKDF2-SHA256 و 210,000 iteration هش می‌شود؛ پس از 5 تلاش ناموفق PIN حساب برای 15 دقیقه قفل می‌شود و OTP نیز ۶۰ ثانیه اعتبار و حداکثر ۵ تلاش دارد.
- API مالک برای فهرست، ساخت، ویرایش، تغییر دسترسی، فعال/غیرفعال‌سازی و ابطال نشست مدیر پیاده‌سازی شده است.
- ساخت حساب و درج مجوزهای اولیه مدیر در یک D1 batch انجام می‌شود. حذف فیزیکی مدیر عمداً ارائه نشده تا سابقه و ارجاعات حفظ شود.
- رابط فارسی و واکنش‌گرای پنل مالک در مسیر `/owner` ساخته و به API مدیریت مدیران متصل شده است؛ تاریخچه ۱۰۰ رویداد اخیر ورود و عملیات مدیریتی نیز در پنل نمایش داده می‌شود. صفحه ورود دومرحله‌ای مدیر و نمایش مجوزهای حساب نیز در `/admin/login` ساخته شده است؛ ابزارهای عملیاتی مدیر هنوز منتقل نشده‌اند.
- GitHub Actions برای TypeScript، بررسی syntax فایل JavaScript پنل و اجرای migrationهای محلی D1 تنظیم شده است.

### اعتبارسنجی
- آخرین اجرای CI روی شاخه مهاجرت با نتیجه success پایان یافته است: `npm run check`، بررسی syntax جاوااسکریپت هر دو پنل، و اجرای محلی هر سه migration موفق بوده‌اند.
- تست SQLite جداگانه نیز ساخت جدول مدیر و درج مجوزها را بررسی کرده است.
- این تست‌ها هنوز جایگزین آزمون end-to-end با مرورگر، Worker محلی و ربات آزمایشی نیستند.

### محدودیت‌های باقی‌مانده
- پنل مالک هنوز روی Cloudflare deploy نشده و ورود تلگرام واقعی در محیط Worker آزمایش نشده است.
- پنل مدیر و APIهای عمومی مدیریت گروه/کانال هنوز کامل منتقل نشده‌اند.
- کد چهاررقمی ذاتاً فضای جست‌وجوی کوچکی دارد؛ قفل حساب و rate limit دفاع اولیه‌اند، اما پیش از تولید بهتر است ورود مدیر به عامل دوم یا PIN طولانی‌تر ارتقا یابد.
- جدول‌های D1 فعلی طرح مقصد پیشنهادی‌اند و هنوز با schema زنده PostgreSQL Render و backup کامل تطبیق داده نشده‌اند.
- D1 تولیدی خالی مانده است؛ migration فقط در محیط محلی CI اجرا شده است.
- Worker deploy نشده، webhook تلگرام ثبت نشده، Render دست‌نخورده است و هیچ پلن پولی فعال نشده است.
